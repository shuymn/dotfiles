# Skill Vocabulary

リポジトリ内の人間向け文書（`README.md`、`docs/**`）および Agent 向け文書（`home/dot_claude/skills/**`、`AGENTS.md` など）を、言い換えのない標準技術用語で一貫して執筆・校正するための基準。

## 文書の役割と情報量コントロール

- **情報量コントロールの基準（共通）:** コード・設定・git 履歴を見れば分かり、気になったときに Agent へ質問すれば済む詳細や、変化が速く陳腐化しやすい一覧・個別メモは書かない。文書に残すのは「Agent が動く前の入口（ブートストラップ）」と「コードだけでは読み取りにくい意図・境界・規約」に絞る。
- **共通制約:** ボキャブラリ統一（標準技術用語）、公開制約（[public-text](../../../home/dot_claude/skills/public-text/SKILL.md)）、現行状態の維持（変更時は現時点の仕様・結論へ書き換え、古い経緯の追記や日記化をしない）。
- **文書の役割区分（5 区分）:**
  1. **入口・ブートストラップ（`README.md`）:** 日本語。目的・3 ツール分担・新規 Mac 立ち上げ・日常入口コマンドと正本への導線だけを持つ。
  2. **設計・運用不変条件（`docs/**`）:** 日本語（実験事前登録 `scripts/kaizen/probe/PREREG.md` は英語）。コードからは読み取りにくい設計根拠・制約・比較を残す。
  3. **リポジトリ保守契約（`AGENTS.md`）:** 英語。所有権境界・禁止事項・変更種別ごとの必須検証を固定する。
  4. **横断の常駐ガードレール（`home/.chezmoitemplates/agents/AGENTS.md`、`CLAUDE.md.tmpl`、`agents/*.md`、`handover/*.md`）:** 英語。全リポジトリ共通の行動境界・環境制約・役割定義を最小限に保つ。
  5. **必要時参照のスキル（`home/dot_claude/skills/**`、`.agents/skills/**`）:** 日本語。判断基準・適用境界・手順を、文字通りの解釈を前提に（lost judgment 防止・例示括弧への `例:`・境界を示すときだけの `Why`・一時的規則への撤去条件）記述する。

## 原則

- **標準技術用語を優先する:** 事前学習の概念に直結する技術用語（`worktree`、`バックグラウンド`、`コンテキスト`、`エッジケース`、`プロパティベーステスト` など）を使い、文学的・和製的な言い換え（`木`、`根`、`見回り`、`清潔`、`番人`、`指紋` など）を避ける。
- **1 概念 1 語:** 同じ概念に別語を混ぜない。1 語が複数概念を兼ねて衝突している語は意味ごとに分離する。
- **判断を落とさない（lost judgment 防止）:** 言い換えで規則の適用範囲や条件を狭めたり曖昧にしたりしない。
  - 全サブエージェント（例: `worker`・`reviewer`・`steward`・設計エージェント）を指す箇所を `worker` に狭めない（`子セッション` を使う）。
  - 本番コード・対象実装の実行を求める箇所を「同等」にぼかさない。
  - 有効性チェックや差分の出所確認では「どの既存パスと同じチェックか」「自分の変更に由来するか」の条件を残す。
  - パーサー出力の例は AST だけに狭めず `パーサーの構文木や DOM ツリー` とする。
- **関連規則との整合:** 上記の「文書の役割と情報量コントロール」、`.stack/writing.md`（文字通りの解釈、例示括弧への `例:`、境界を示すときだけの `Why`）、`public-text` に従う。

### 多義語の分離

文脈で意味が異なる語は一律置換せず、意味ごとに正規語へ分ける。

- `経路`: 進行上の重要経路は `クリティカルパス`、HTTP ルートは `エンドポイント`、処理分岐は `パス`、生成〜破棄は `ライフサイクル`。
- `段`: 手順の単位は `ステップ` / `フェーズ`、証拠の強さの段階は `レベル`、対策の優先順位は `上位の対策`。
- 置換しない別語: `背景`（経緯・説明の文脈）、`確定版`、`文脈`（視覚・UI の使用文脈）、`丸い塊`、`下端の画素行`、`手段`。

## 手順

1. 対象の `README.md`、`docs/**/*.md`、`home/dot_claude/skills/**/*.md` を走査し、対照表の「避ける語」と多義語の混在を洗い出す。
2. 依頼がレビュー・校正の指摘のみなら、ファイルを編集せず該当箇所と置換案を返す。作成・編集の依頼なら、意味と境界を保ったまま正規語へ置換し、見出し名を変えた場合はリポジトリ内で見つかった参照（例: 他スキル、`home/dot_claude/attention/items.json`、`docs/`）も同時に更新する。
3. 編集した場合は次をすべて確認して完了とする:
   - 編集した文書と `home/dot_claude/skills/**` の相対 Markdown リンクがすべて解決する。
   - 変更した旧見出し・旧ファイル名への残存参照がない。
   - 差分が `git diff --check` と `public-text` スキルに適合する（公開前の `stack-public check` 実行はコミット・PR 公開手順に委ねる）。
   - Agent 向け文書の複数ファイルにまたがる書き換えでは、オーケストレーターがレビューで lost judgment（条件の狭まり・抜け）がないか確認する（worker は差分と検証結果を返すまでとする）。
