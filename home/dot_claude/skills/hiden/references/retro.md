# レビュー台帳と振り返り

## 台帳（トリアージのたび）

- 公開リポジトリの外の `~/.claude/review-ledgers/<repo>.md` に置く。
- 1 指摘 1 行で、日付・対象とラウンドとレビューの区分（[review.md](review.md) の「いつ」）・重要度・種類・要約・対応（採用／見送りと理由／作り直し）・直した所（コード／計画／両方／—）・仕組みで防げたかを書く。
- 見送りも、指摘ゼロのラウンドも、エージェントの手順違反も記録する。見送りが続くなら、レビューに渡すコンテキストが足りていない。
- マージ後に見つかった欠陥（例: revert、障害、オーナーの報告、この変更が入れたと後で分かった不具合）は、見逃しとして、`stack-observe` が見逃しとして数える行の書式（`shuymn/stack` の `docs/design/phase3-cycle.md` §3.3 の `ledgers`）で、対象の PR・欠陥・根拠のリンクだけを添えて記録する。Why: 出た指摘だけでは、レビューの形を変えて何を見逃すかが分からない。

## 振り返り（フェーズの区切りか、マージ済み PR 約 10 本の、早いほう）

次の指示書を出す前に行う。

1. compaction の後の読み直しを確かめる。`${XDG_STATE_HOME:-~/.local/state}/claude/compactions.jsonl`（項目は書き込む `~/.claude/hooks/log-compact-summary.sh` の冒頭）のうち、前回以降でこのリポジトリを `cwd` とする行の `transcript_path` から境界を探す。境界時点の復元状態が名指しした進行中のステップのうち境界後に再開したものごとに、そのステップの規則がある hiden reference を、境界からそのステップを再開した最初の操作までの間に読み直したかを transcript で見る（その操作より後に読んだものも見逃しに数える）。見逃しのうち、ステップを名指ししたキット自身の注意の項目のブロック（タグと `path` は `shuymn/stack` の `docs/design/phase2-core.md` §4.1.1。`path` で同じキットと照合する）にその境界で読み直しの項目が出ていたものだけを、セッション、境界、キット、読むべきだった reference、再開した最初の操作の位置を付けて台帳に 1 行ずつ書く。
2. 前回以降の行を種類ごとに数え、繰り返す種類と、単発でも見逃しを扱う。同じ主張への反例の繰り返し、計画の直しの連続、テストに増える特例は、コードではなく計画の向きが誤っている兆候として読み、目的の層（[orchestration.md](orchestration.md)）を実物で確かめ直す。
3. 種類ごとに、共通の形と、既存のテスト・型・規則がそれを止められなかった理由を書く。見逃しには、捕まえられた工程（計画、レビュー、テスト、CI、実物。複数・不明も可）を補う。区分の分け違いなら分け直し、共通する不足が確かめられたときだけ区分の基準を上げる。レビューの形を変えたら、既知の見逃しの修正前の差分にかけ直して比べ、件数の増減だけで良し悪しを決めない。
4. 対策を 0〜2 個選ぶ。新しい枠組みより既存のものを強め、[verification.md](verification.md) の順で効くものから選ぶ。文の対策には上位の対策が効かない理由を添える。
5. オーケストレーター自身の手順の逸脱も振り返り、仕組みか既存規則の訂正にする（[attention.md](attention.md)）。
6. 結果を台帳に追記する。
7. オーナーに、新しいセッションで `/wasure` を走らせる時期だと伝える。`~/.claude/review-ledgers/global.md` の最新の行と今のモデル ID が違えば、それも伝える。

## 文書整理（振り返りと同じ周期）

- 残すもの: 不変条件、上限とその根拠、外部仕様の癖とその参照、利用者・運用者に要る情報。削るもの: コードで分かること、経緯、重複（正本は 1 か所）。
- 範囲は前回以降に触ったファイル。挙動は変えず、テストで確かめる。リリース済みの変更履歴には触らない。
- 変更前からある問題は積み残しに回す。
