# Codex レビュー

Codex はレビュー専用で、実装はさせない。オーナーは Codex レビューを経た内容だけを確定版として扱う。

## 実行

- codex-plugin-cc の `codex:rescue` を `--read-only --prompt-file <file>` で使い、依頼文はファイルに書く。
- r2 以降の確認ラウンドは、新しいスレッドにせず `--thread <前のラウンドの id>` で続け、修正範囲と前の指摘ごとの対応だけを渡す。

## いつ

- 最低限は、実装前の計画と実装後のコードに各 1 回。直す指摘が出たラウンドの後は、修正を確かめるラウンドを足す。直す指摘が無ければ、そのラウンドで終える。
- 資料は骨子と完成版で各 1 回。追記したら、追記部分だけをもう一度。
- simplify はこの回数に数えない。

## 依頼の書式

共通: 範囲を限り、変更の目的、設計書・指示書・ブランチが足したもの、確かめたい問いを名指しする。HIGH/MEDIUM は file:line・シナリオ・修正案を付けて重要度順に、LOW は 1 行ずつ返させる。

### 計画と資料

次の観点を同じ重みで見させる。

1. **設計:** 外部仕様との契約、データモデルと層、単純さとコスト、リポジトリ全体との一貫性。
2. **バグの芽:** 端の場合、全方向のページング、競合、再開、エラー処理。
3. **セキュリティ:** 脅威モデルがあればその不変条件。
4. **テスト:** 主張ごとのテストが、修正を戻して落ちる形か、空振りのフィクスチャが無いか。
5. **主張の一覧**（[orchestration.md](orchestration.md) の「目的の層と計画の層」）: 出どころの無い主張、目的や範囲を超える主張、破れたことを示しようがない主張、触る部分の既存の要件で一覧から漏れたもの、脅威モデルが受け入れ済みとする制限を守ろうとする主張を挙げさせる。

### コード

「レビューして」とは頼まず、計画で決めた主張の一覧を渡して反証させる。主張ごとに次のどれかを返させる。

- **反証の証拠**（下の「コードレビューの証拠」のどれか）。
- **反証できず、守るテストあり:** そのテスト名。そのテストが主張を壊したコードでも落ちない（空振りのフィクスチャ、別の経路）なら、それを反証の証拠として返す。
- **反証できず、守るテストなし:** テストの欠落として扱う。

あわせて次の 2 つを問う。

- 計画に従うと目的が悪くなる所、主張そのものが誤っている所はどこか。証拠は、目的の層の条件が実物で落ちる例か、外部仕様との矛盾。計画の層がすべて通ることは前提にしない。
- 一覧に無いが、変更した振る舞いに当たる既存の正本の要件（設計書の契約、脅威モデルの守るもの）を破っている所。出典を挙げさせ、計画の漏れとして扱う。正本に無い防御や汎用化をここで足させない。

Why: 抽象的なレビューは細かい指摘と要件外の防御に流れ、台帳ではコードの指摘の多くがテストがあれば機械で捕まえられたものだった。反証の対象を計画の段で決めておけば、レビューの手間を実行できる証拠に向けられる。

## コードレビューの証拠

コードの指摘で採れるのは、確かめられる証拠のある指摘だけにする。証拠の無い推測は LOW までとする。計画と資料の指摘は、引用した本文・出どころ・シナリオ・設計の論拠で判断する。

- 実行できる反例: そのまま走らせられるテストのコードか再現のコマンド（入力、期待、今のコードで起きることを含む）。規模やアロケーションのテストを含む。
- 競合なら、ソースの位置を挙げた具体的な割り込みの順序、同期についての前提、入れるべき待ち点（[verification.md](verification.md) の決定的な並行性のテスト）。
- 引用した要件や外部仕様（`file:line`）と実装との矛盾。
- コードと想定する利用規模から導いた資源の計算。

## 取捨選択

1. **反例を走らせる:** 実行できる反例は自分で走らせる。判定の前に、テストが実際に走ったこと、主張する本番の経路を通ったこと、期待が主張に根拠を持つことを確かめる（[verification.md](verification.md) の「証拠の強さ」）。主張どおりの理由で落ちたものだけを再現とする（コンパイルの失敗は再現ではない）。走らなかったか効いていないものは結論なし、正しく作って通ったものは、その反例を退ける。リポジトリに変異テスト（`cargo-mutants --in-diff` など）があれば、主張を守るとされたテストが壊したコードで本当に落ちるかもそれで確かめる。
2. **実行できない証拠は採る前に確かめる:** 割り込みの順序はソースで辿り、資源の計算は定数と経路を読み直す。重要度は示された影響で決め、確かめた段は別に記録する。
3. **脅威モデルで振り分ける:** 脅威の前提が採否を決める指摘だけに使い、普通の正しさは設計の契約で決める。守るものを破るなら採る（既存の上限を回帰の天井として残すことも守るものに含む）。受け入れ済みの制限は、その条件がすべて当てはまり、守るものを何も破らないときだけ見送る。どちらにも当たらない新しい守りの要求や、方針どうしの食い違いは直さずにオーナーへ相談し、方針が変わるなら先に脅威モデルを直す。
4. **目的に照らす:** 指摘ごとに「この変更の目的に必要か」「実際に起こるか」で採否を決め、理由を添えて報告する。起こり得ない入力への防御や要件外の汎用化は見送る。意味や予算の配分を変える修正は、送る前に上限と外部仕様に照らして確かめる。Why: Codex は目的を見失って過剰防御や仕組みの追加を提案しがちで、依頼文で目的を伝えてもその傾向は残る。
5. **計画への指摘は計画を直す:** 計画が誤っている、主張が漏れているという指摘は退けず、計画を直してから、要ればコードを直す。オーナーと合意した目的や範囲に触れるなら、[SKILL.md](../SKILL.md) の手順 4 のとおり相談する。

## 回し方

ラウンドの回数に上限は無く、必要なら 3 回以上回してよい。ただし指摘を 0 件にすることは目的ではない。ラウンドのたびに、この変更の目的に照らしてまだ直す価値のある指摘かを確かめる。1 つの変更で同じ種類の指摘が 3 ラウンド続いたら、修正を重ねる前に作り直す（[orchestration.md](orchestration.md) の「作り直しの向き」）か、制約として文書化して見送る。
