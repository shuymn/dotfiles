# Codex レビュー

Codex はレビュー専用で、実装はさせない。オーナーは Codex レビューを経た内容だけを確定版として扱う。計画段階で潰した欠陥がいちばん安い。

## 実行

- codex-plugin-cc の `codex:rescue` を `--read-only --prompt-file <file>` で使い、依頼文はファイルに書く。
- r2 以降の確認ラウンドは、新しいスレッドにせず `--thread <前のラウンドの id>` で続け、修正範囲と前の指摘ごとの対応だけを渡す。

## いつ

- 最低限は、実装前の計画と実装後のコードに各 1 回。直す指摘が出たラウンドの後は、修正を確かめるラウンドを足す。直す指摘が無ければ、そのラウンドで終える。
- 資料は骨子と完成版で各 1 回。追記したら、追記部分だけをもう一度。
- simplify はこの回数に数えない。

## 依頼の書式

- 範囲を限り、変更の目的、設計書・指示書・ブランチが足したもの、確かめたい問いを名指しする。
- HIGH/MEDIUM は file:line・シナリオ・修正案を付けて重要度順に、LOW は 1 行ずつ返させる。
- 次の 4 観点を同じ重みで見させる。
  1. **バグ:** 端の場合、全方向のページング、競合、再開、エラー処理。
  2. **設計:** 外部仕様との契約、データモデルと層、単純さとコスト、リポジトリ全体との一貫性。
  3. **セキュリティ:** 脅威モデルがあればその不変条件。
  4. **テスト:** 回帰で落ちるか、空振りのフィクスチャが無いか。

## 取捨選択

Codex は目的を見失って、過剰防御や仕組みの追加を提案しがちで、依頼文で目的を伝えてもその傾向は残る。指摘をそのまま直す前に、指摘ごとに「この変更の目的に必要か」「実際に起こるか」で採否を決め、理由を添えて報告する。起こり得ない入力への防御や要件外の汎用化は見送る。意味や予算の配分を変える修正は、送る前に上限と外部仕様に照らして確かめる。

## 回し方

ラウンドの回数に上限は無く、必要なら 3 回以上回してよい。ただし指摘を 0 件にすることは目的ではない。ラウンドのたびに、この変更の目的に照らしてまだ直す価値のある指摘かを確かめる。1 つの変更で同じ種類の指摘が 3 ラウンド続いたら、修正を重ねる前に作り直す（[orchestration.md](orchestration.md) の「作り直しの向き」）か、制約として文書化して見送る。
