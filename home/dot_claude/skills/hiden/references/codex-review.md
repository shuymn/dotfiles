# Codex レビュー

Codex はレビュー専用で、実装はさせない。オーナーは Codex レビューを経た内容だけを確定版として扱う。

## 実行

- T3 Code の中では、codex-plugin-cc ではなく `delegate_task`（`role: "review"`、モデル `gpt-6.1-sol`）で頼み、編集しないことを依頼文に書く。`reasoningEffort` は費用を抑えるより成果を最大にする向きで、下の「いつ」の区分と問いの難しさに合わせて選ぶ。r2 以降の確認ラウンドも新しい `delegate_task` にし、修正範囲と前の指摘ごとの対応を渡す。
- それ以外では codex-plugin-cc の `codex:rescue` を `--read-only --prompt-file <file>` で使い、依頼文はファイルに書く（モデルと労力は Codex の設定に従う）。r2 以降の確認ラウンドは、新しいスレッドにせず `--thread <前のラウンドの id>` で続け、修正範囲と前の指摘ごとの対応だけを渡す。

## いつ

区分は行数や revert のしやすさではなく、変更後に何に作用するかで決め、迷ったら上の区分にする。simplify は回数に数えない。

- **低**（文書・設定・テストだけ、数行の修正、短い資料）: 計画と主張の一覧は作らず、完成した差分に 1 回、計画と資料の観点で。修正の確認は、修正が意味を変えたときだけ。
- **標準**（普通のコード、長い資料）: 計画（資料は骨子）と完成物に各 1 回。直す指摘が出たら確認のラウンドを足す。
- **高**（認可、課金、データの移行、公開の API とデータ形式、CI・リリース・インストーラ、セキュリティの境界、戻せない操作）: 標準に加え、確認のラウンドを省かず、マージの前に目的の層を実物で確かめる（本番でしか確かめられないものは隔離した環境で本物の経路を通す）。できなければ未検証と報告し、扱いをオーナーと決めるまでマージしない。

Why: 一律の回数では、文書だけの変更にも計画・完成・確認のラウンドが重なり、人の時間を検証の少ない所に使う。

## 依頼の書式

範囲を限り、変更の目的、設計書・指示書・ブランチが足したもの、確かめたい問いを名指しする。検査や監査（テストの仕組み、lint、計画の監査）のレビューでは、それが何から守るか（書き手のうっかりか、すり抜けようと組んだ入力か）を依頼に書く。Why: 監査の許可を、すり抜け用に組んだ SQL の反例で 3 ラウンド追い、範囲を切り直すことになった。HIGH/MEDIUM は file:line・シナリオ・修正案を付けて重要度順に、LOW は 1 行ずつ返させる。

**計画と資料**は次を同じ重みで見させる。

1. **設計:** 外部仕様との契約、データモデルと層、単純さとコスト、リポジトリ全体との一貫性。
2. **バグの芽:** 端の場合、全方向のページング、競合、再開、エラー処理。
3. **セキュリティ:** 脅威モデルがあればその不変条件。
4. **テスト:** 主張ごとのテストが、修正を戻して落ちる形か、空振りのフィクスチャが無いか。
5. **主張の一覧**（[orchestration.md](orchestration.md) の「目的の層と計画の層」）: 出どころが無い、目的や範囲を超える、破れたことを示しようがない、既存の要件が漏れている、受け入れ済みの制限を守ろうとしている主張。

**コード**は「レビューして」と頼まず、主張の一覧を渡して反証させる。主張ごとに、反証の証拠（下）、守るテストの名前、守るテストが無いこと（テストの欠落）のどれかを返させる。守るテストが主張を壊したコードでも落ちないなら、それも反証とする。あわせて 2 つを問う。

- 計画に従うと目的が悪くなる所、主張そのものの誤り。証拠は目的の層の条件が実物で落ちる例か外部仕様との矛盾で、計画の層がすべて通ることは前提にしない。
- 一覧に無い既存の要件を破る所。要件は正本（設計書の契約、脅威モデルの守るもの）と、計画が変えるとしていない今の振る舞い（base で通り変更後に落ちる反例で示す回帰の候補。予算内の内部の順序のような偶然の振る舞いは除く）。正本にも今の振る舞いにも無い防御や汎用化は足させない。

Why: 抽象的なレビューは細かい指摘と要件外の防御に流れ、コードの指摘の多くはテストがあれば機械で捕まえられた。反証の対象を計画で決めておけば、手間を実行できる証拠に向けられる。

## 反証の証拠

コードの指摘で採るのは次のどれかを持つものだけで、無ければ LOW までとする。計画と資料の指摘は、引用した本文・出どころ・シナリオ・設計の論拠で判断する。

- そのまま走らせられるテストか再現のコマンド（入力、期待、今のコードで起きること。規模やアロケーションのテストを含む）。
- 競合なら、ソースの位置を挙げた割り込みの順序と、入れるべき待ち点（[verification.md](verification.md) の決定的な並行性のテスト）。
- 引用した要件や外部仕様（`file:line`）と実装との矛盾。
- コードと想定する利用規模から導いた資源の計算。

## 取捨選択

1. **反例は自分で走らせる:** テストが走ったこと、主張する本番の経路を通ったこと、期待が主張に根拠を持つことを確かめ（[verification.md](verification.md) の「証拠の強さ」）、主張どおりの理由で落ちたものだけを再現とする。走らなかったか効いていないものは結論なし、正しく作って通ったものは退ける。変異テスト（`cargo-mutants --in-diff` など）があれば、守るとされたテストが本当に落ちるかもそれで確かめる。走らせられない証拠は、ソースと定数を辿り直してから採る。重要度は示された影響で決める。
2. **脅威モデル:** 脅威の前提が採否を決める指摘だけに使い、普通の正しさは設計の契約で決める。守るもの（回帰の天井として残す上限を含む）を破るなら採る。受け入れ済みの制限は、条件がすべて当てはまり守るものを破らないときだけ見送る。どちらでもない新しい守りや方針の食い違いは、直さずにオーナーへ相談し、方針が変わるなら先に脅威モデルを直す。
3. **目的に照らす:** 「この変更の目的に必要か」「実際に起こるか」で採否を決め、理由を添えて報告する。起こり得ない入力への防御や要件外の汎用化は見送る。意味や予算の配分を変える修正は、上限と外部仕様に照らしてから送る。Why: Codex は目的を見失って過剰防御や仕組みの追加を提案しがちで、依頼文で目的を伝えてもその傾向は残る。
4. **計画への指摘は計画を直す:** 退けず、計画を直してから要ればコードを直す。合意した目的や範囲に触れるなら [SKILL.md](../SKILL.md) の手順 4 のとおり相談する。

## 回し方

ラウンドの回数に上限は無いが、指摘を 0 件にすることは目的ではない。ラウンドのたびに、目的に照らしてまだ直す価値のある指摘かを確かめる。1 つの変更で同じ種類の指摘が 3 ラウンド続いたら、修正を重ねる前に作り直す（[orchestration.md](orchestration.md) の「作り直しの向き」）か、制約として文書化して見送る。
