# 複数 PR にわたる開発

メインのセッションは設計の取捨選択・統合・検証・PR・マージを担い、実装は範囲を切ったエージェントに任せる。メインの文脈は設計判断と統合のために空けておく。

## 委任の原則

- **続きの送り先:** 同じ領域の続き（ターン上限からの再開、レビューと simplify の修正、次の作業）は、キャッシュが温かいうちか、そのワークツリーや未コミットの変更が要るときだけ自分が立てた同じエージェントに送る（`SendMessage`、T3 Code では `t3_thread_send`）。それ以外は指示書・前の報告・ブランチを渡して新しく立てる。相談にはすぐ答える（待つとキャッシュが切れる）。
- **T3 Code の中では:** 実装エージェントは `delegate_task`（`isolation: "worktree"`）の子として起動し、依頼文は固定の 1 行で `~/.claude/agents/opus-worker.md` の本文に従わせる（相談は `AskUserQuestion`）。子は通知で起こすので、`t3_thread_wait` や見回りで待たない。オーケストレーターは対象リポジトリの T3 プロジェクトの中で動かす。Claude のモデルと労力は成果を最大にする向きで選ぶ。
- **長いセッションと compaction:** 本質と状態はキット（`state.md` か `NORTH.md`、`units.json`、`bin/board`）に置き、フックが開始と compaction の後に文脈へ戻す（[attention.md](attention.md)）。

## 1 PR の段

1. **設計:** 設計エージェントに設計書を書かせる。渡すもの: 対象の範囲、参照すべき既存コードと一次資料（手元のソース）、守るべき不変条件と上限、同じ型の問題がほかにどこで効いているかの棚卸し、構造の選択肢との比較（[judgment.md](judgment.md)）。完了条件: 設計書に決定・根拠・テスト方針・測定するもの、下の「目的の層と計画の層」の 2 つの一覧が揃っている。
   - 調査や点検を Codex に任せた後も、設計書は設計エージェントに書かせ、Codex の調査結果は資料として渡す。Why: 原因を調べた Codex に設計まで頼むと、次の段で Codex が自分の設計をレビューすることになる。
   - Web 画面（HTML・CSS・クライアントのスクリプト）を触るなら、設計の前に modern-web-guidance スキルで関係するガイドを引き、設計書と指示書に渡す。
2. **設計レビュー:** [codex-review.md](codex-review.md) のとおりに Codex に読ませる。採った指摘は設計書を直すか、小さなものは指示書への追補（amendments）に書く。ラウンドのたびに、計画の全体を最初の目的と範囲に照らして見直し、出どころの無い主張と範囲外の機能・上限・防御はその場で外す。範囲内の義務が 3 ラウンド増え続けたら、足し続けずに範囲を切り直す（合意した範囲が変わるならオーナーに相談）。Why: 主張の一覧を中心に置くと、要件外の防御がコードの段から計画の段へ移ってくる。
3. **指示書:** 設計書と追補のパス（中身は貼らず、根拠は `file:line` で指す）、範囲と範囲外（書く前に issue を本文とコメントまで読み直し、その issue 番号でコミット履歴を引いて、済んでいる部分を外す。Why: issue の記述は実装より遅れ、直し済みの範囲を含みうる）、完了条件（エージェントが自分で走らせて合否を読めるコマンド: テスト、ビルド、出力を固定値と比べるスクリプト、`verify-<app>`）、測定・報告させるもの、[subagent-brief.md](subagent-brief.md) のとおりの固定の 1 行とその作業が当たる束を渡す。照合や分類の条件を足す変更では、完了条件に、手元にある本物の入力へその条件を当てて、当たった先の一覧を報告させることを入れる（設計の段でも同じ確かめをする）。Why: 語句の照合は、テスト用の入力には無い本物の入力の一部（例: 別のタグの一部）まで拾いうる。
4. **実装:** T3 Code の外では、`subagent_type: "opus-worker"`、`isolation: "worktree"` で 1 体ずつ起動する（専用のワークツリーが `agent-<id>` ブランチで作られる。PR の前に `git branch -m` で作業名に付け替える）。早めにこまめにコミットさせ、報告は [subagent-brief.md](subagent-brief.md) の「報告の確認」のとおりに確かめる。
5. **PR とマージ:** [commit-pr.md](commit-pr.md) の手順で進める。委任しているときは次が加わる。
   - レビューと simplify で採った指摘はすべて台帳に記録する（[retro.md](retro.md)）。
   - push は、そのワークツリーの worker が報告を終えてから行う。
   - simplify は Codex に報告だけをさせ、実装エージェントに適用させる。依頼文の冒頭で、途中で撤回した実装を名指しして残骸を探させる。

## 目的の層と計画の層

設計書には 2 つの一覧を分けて書き、コードレビューはこれを反証する（[codex-review.md](codex-review.md)）。

- **目的の層:** 依頼から書いた受け入れ条件。条件ごとに、依頼の出どころ、場面、外から観察できる結果と失敗、実物（アプリ、CLI）での確かめ方を書く（書けるものは EARS）。主観で決まるもの（操作感、見た目）は数字を作らずオーナーの評価とし、確かめる手段が無ければ未検証とする。オーナーが依頼や会話で決めた条件は合意済みとし、曖昧な依頼の解釈で手順 4（[SKILL.md](../SKILL.md)）に当たること（求める結果、範囲）が決まるときだけ、固める前にまとめて推奨を添えて合意を取る。確かめ方や測り方は手法の選択として扱う。合意したものを変えるときは、目的に照らした理由と影響を報告する。
- **計画の層:** 目的の層から導いた主張で、仮説として扱う。EARS の 1 行ずつに、出どころ（依頼、設計書の節、脅威モデルの項目）と確かめるテストを添え、契約の索引（主張ごとに検証するテストを挙げ、テストが検査するもの）があればそこに書く。受け入れ済みの制限は主張にしない。ただし「受け入れ済み」と書けるのは、オーナーの承認を引用できるものか、目的を損なわない根拠を引けるものだけで、根拠の無い副作用は受け入れた制限にせず欠陥として計画を直す（[SKILL.md](../SKILL.md) の手順 5）。目的の層と食い違ったら計画の層を直す。

段階の区切りでは、目的の層を実物で確かめ直す。Why: 反証は計画どおりかしか確かめないので、目的の層を落ちうる形で計画の外に置かないと、誤った計画が全部の主張を通したまま進む。

## 段をまたぐ規則

- **点検から始める:** 似た欠陥が広く散っていそうなら、まず Codex に候補を列挙させて表にする。それを独立した PR に分け、全項目を消し込むまで続ける。
- **作り直しの向き:** 同じ種類の指摘が続いたら、仕組みを足すより次へ寄せる。
  - 既存の単品の操作を、上限つきのラウンドで繰り返し使う。
  - 保守的な既定値と、レビュー済みの明示的な opt-in にする。
  - 上限は、測った値ではなく定数からテストで導く。
- **振り返り:** [retro.md](retro.md) の時期と手順で行う。
- **ブランチは切る直前に fetch する:** ワークツリーは、fetch と同じコマンドの中で、fetch した base から作る。Why: 古い base には main で直し済みの失敗が残る。
