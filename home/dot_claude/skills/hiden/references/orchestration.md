# 複数 PR にわたる開発

メインのセッションは設計の取捨選択・統合・検証・PR・マージを担い、実装は範囲を切ったエージェントに任せる。メインの文脈は設計判断と統合のために空けておく。設計段階でレビューを一度挟むと、実装後の手戻りが大きく減る。

## 委任の原則

委任の費用の大半は、エージェントが文脈を組み直すことにある。組み直しを減らし、メインには判断に要る結論だけを戻す。

- **単位:** 渡すのは独立した大きな単位（1 PR、広い調査）だけ。数回のツール呼び出しで済む作業と、自分の作業の確かめ直しはメインで行う。
- **1 領域 1 エージェント:** 同じ領域の続き（ターン上限からの再開、レビューと simplify の修正、次の作業）は、新しいエージェントを立てずに `SendMessage` で同じエージェントに送る。文脈がキャッシュに残ったまま続けられる。相談が届いたらその場で答える（待たせるとキャッシュが切れる）。
- **渡すのは場所、戻すのは結論:** 指示書には設計書のパスと `file:line` を書き、中身はエージェントに読ませる。報告は結論とパスに絞らせ、長い結果は指示書で決めたファイルに書かせて、メインは必要なときだけ読む。

## 1 PR の段

1. **設計:** Plan エージェントに設計書を書かせる。渡すもの: 対象の範囲、参照すべき既存コードと一次資料（手元のソース）、守るべき不変条件と上限、同じ型の問題がほかにどこで効いているかの棚卸し、構造の選択肢との比較（[judgment.md](judgment.md)）。完了条件: 設計書に決定・根拠・テスト方針・測定するものが揃っている。
2. **設計レビュー:** [codex-review.md](codex-review.md) のとおりに Codex に読ませる。採った指摘は設計書を直すか、小さなものは指示書への追補（amendments）に書く。
3. **指示書:** 設計書と追補のパス、範囲、測定・報告させるもの、[subagent-brief.md](subagent-brief.md) の規則とリポジトリ固有の共通規則をまとめて渡す。
4. **実装:** 実装エージェントを `isolation: "worktree"` で 1 体ずつ起動する（専用のワークツリーが `agent-<id>` ブランチで作られる。PR の前に `git branch -m` で作業名に付け替える）。早めにこまめにコミットさせる。報告を受けたら、規則違反、コミットの件名、テスト件数、設計からの逸脱とその理由を確かめる。
5. **PR とマージ:** [commit-pr.md](commit-pr.md) の手順で進め、CI が緑になったらマージする。委任しているときは次が加わる。
   - レビューと simplify で採った指摘はすべて台帳に記録する（[retro.md](retro.md)）。
   - simplify は Codex に報告だけをさせ、実装エージェントに適用させる。依頼文の冒頭で、途中で撤回した実装を名指しして残骸を探させる。
   - push は pre-push フックが走るので、1 本ずつ行う。

## 段をまたぐ規則

- **点検から始める:** 似た欠陥が広く散っていそうなら、まず Codex に候補を列挙させて表にする。それを独立した PR に分け、全項目を消し込むまで続ける。
- **作り直しの向き:** 同じ種類の指摘が続いたら、仕組みを足すより次へ寄せる。
  - 既存の単品の操作を、上限つきのラウンドで繰り返し使う。
  - 保守的な既定値と、レビュー済みの明示的な opt-in にする。
  - 上限は、測った値ではなく定数からテストで導く。
- **振り返り:** 約 10 PR ごとに台帳を集計する（[retro.md](retro.md)）。
