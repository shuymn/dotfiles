# 複数 PR にわたる開発

オーケストレーターは設計の取捨選択・統合・検証・PR・マージを担い、実装は範囲を切った worker に任せる。オーケストレーターのコンテキストは設計判断と統合のために空けておく。

## 委任の原則

- **続きの送り先:** 同じ領域の続き（例: ターン上限からの再開、レビューと simplify の修正、次の作業）は、プロンプトキャッシュが有効なうちか、その worktree や未コミットの変更が要るときだけ自分が起動した同じ worker に名指しで送る。それ以外は指示書・前の報告・ブランチを渡して新しく起動する。相談にはすぐ答える（待つとプロンプトキャッシュが切れる）。
- **起動と待ち:** worker は 1 体ごとに専用の worktree で起動し、指示書は [subagent-brief.md](subagent-brief.md) のとおりに書く。仮のブランチ名（例: `Agent` の `subagent_type: "opus-worker"`、`isolation: "worktree"` の `agent-<id>`）で始まったら、PR の前に `git branch -m` で作業名に付け替える。子セッションは終了通知で起こすので、ポーリングや待機コマンドで待たない。委任と引き継ぎの前に、シェルの cwd だけでなくセッション自体が対象リポジトリに属することを確かめる。モデルと労力は成果を最大にする向きで選ぶ。
- **長いセッションと compaction:** 委任の前にキットを作り、本質と状態をキットに置く（[attention.md](attention.md)）。

## 1 PR のフロー

1. **設計:** 設計エージェントに設計書を書かせる。渡すもの: 対象の範囲、参照すべき既存コードと一次資料（手元のソース）、守るべき不変条件と上限、同じ型の問題がほかにどこで効いているかの棚卸し、構造の選択肢との比較（[judgment.md](judgment.md)）。完了条件: 設計書に決定・根拠・テスト方針・測定するもの、下の「目的の層と計画の層」の 2 つの一覧が揃っている。
   - 調査や点検を Codex に任せた後も、設計書は設計エージェントに書かせ、Codex の調査結果は資料として渡す。Why: 原因を調べた Codex に設計まで頼むと、次のステップで Codex が自分の設計をレビューすることになる。
   - Web 画面（例: HTML・CSS・クライアントのスクリプト）を触るなら、設計の前に `modern-web-guidance` スキルで関係するガイドを引き、設計書と指示書に渡す。
2. **設計レビュー:** [review.md](review.md) のとおりに読ませる。採った指摘は設計書を直すか、小さなものは指示書への追補（amendments）に書く。ラウンドのたびに、計画の全体を最初の目的と範囲に照らして見直し、出どころの無い主張と範囲外の機能・上限・防御はその場で外す。範囲内の義務が 3 ラウンド増え続けたら、足し続けずに範囲を切り直す（合意した範囲が変わるならオーナーに相談）。
3. **指示書:** 設計書と追補のパス（中身は貼らず、根拠は `file:line` で指す）、範囲と範囲外（書く前に issue を本文とコメントまで読み直し、その issue 番号でコミット履歴を引いて、済んでいる部分を外す。Why: issue の記述は実装より遅れ、直し済みの範囲を含みうる）、完了条件（worker が自分で走らせて合否を読めるコマンド。例: テスト、ビルド、出力を固定値と比べるスクリプト、`verify-<app>`）、測定・報告させるもの、[subagent-brief.md](subagent-brief.md) のとおりの固定の 1 行とその作業が当たるルールブロックを渡す。照合や分類の条件を足す変更では、完了条件に、手元にある本物の入力へその条件を当てて、当たった先の一覧を報告させることを入れる（設計フェーズでも同じ確かめをする）。Why: 語句の照合は、テスト用の入力には無い本物の入力の一部（例: 別のタグの一部）まで拾いうる。
4. **実装:** 上の「起動と待ち」のとおりに起動する。早めにこまめにコミットさせ、報告は [subagent-brief.md](subagent-brief.md) の「報告の確認」のとおりに確かめる。
5. **PR とマージ:** [commit-pr.md](commit-pr.md) の手順で進める。委任しているときは次が加わる。
   - レビューと simplify の結果（見送りや指摘ゼロのラウンド、手順違反を含む）は [retro.md](retro.md) のとおり台帳に記録する。
   - push は、その worktree の worker が報告を終えてから行う。
   - simplify は Codex に報告だけをさせ、worker に適用させる。依頼文の冒頭で、途中で撤回した実装を名指しして残骸を探させる。

## 目的の層と計画の層

設計書には 2 つの一覧を分けて書き、コードレビューはこれを反証する（[review.md](review.md)）。

- **目的の層:** 依頼から書いた受け入れ条件。条件ごとに、依頼の出どころ、場面、外から観察できる結果と失敗、実物（例: アプリ、CLI）での確かめ方を書く（書けるものは EARS）。主観で決まるもの（例: 操作感、見た目）は数値を作らずオーナーの評価とし、確かめる手段が無ければ未検証とする。オーナーが依頼や会話で決めた条件は合意済みとし、曖昧な依頼の解釈で手順 4（[SKILL.md](../SKILL.md)）に当たること（求める結果、範囲）が決まるときだけ、固める前にまとめて推奨を添えて合意を取る。確かめ方や測り方は手法の選択として扱う。合意したものを変えるときは、目的に照らした理由と影響を報告する。
- **計画の層:** 目的の層から導いた主張で、仮説として扱う。EARS の 1 行ずつに、出どころ（例: 依頼、設計書の節、脅威モデルの項目）と確かめるテストを添え、契約の索引（主張ごとに検証するテストを挙げ、テストが検査するもの）があればそこに書く。受け入れ済みの制限は主張にしない。ただし「受け入れ済み」と書けるのは、オーナーの承認を引用できるものか、目的を損なわない根拠を引けるものだけで、根拠の無い副作用は受け入れた制限にせず欠陥として計画を直す（[SKILL.md](../SKILL.md) の手順 5）。目的の層と食い違ったら計画の層を直す。

フェーズの区切りでは、目的の層を実物で確かめ直す。Why: 反証は計画どおりかしか確かめないので、目的の層を落ちうる形で計画の外に置かないと、誤った計画が全部の主張を通したまま進む。

## ステップをまたぐ規則

- **点検から始める:** 似た欠陥が広く散っていそうなら、まず Codex に候補を列挙させて表にする。それを独立した PR に分け、全項目を消し込むまで続ける。
- **作り直しの向き:** 同じ種類の指摘が続いたら、仕組みを足すより次へ寄せる。
  - 既存の単品の操作を、上限つきのラウンドで繰り返し使う。
  - 保守的なデフォルト値と、レビュー済みの明示的な opt-in にする。
  - 上限は、実測値ではなく定数からテストで導く。
- **振り返り:** [retro.md](retro.md) の時期と手順で行う。
- **ブランチは切る直前に fetch する:** worktree は、fetch と同じコマンドの中で、fetch した base から作る。Why: 古い base には main で直し済みの失敗が残る。

## 自律でループを回すとき

オーナーが席を外し、考えて試して自分たちで評価する周回を任されたときの規則。

- **周回の前に目的を書く:** その周回が目的のどの部分を動かすのか、観察できる結果と終える条件を書く（測れるものは、どの数値をいくつからいくつへ）。書けない周回は走らせない。主観で決まる結果はオーナーの評価に回す。会話の流れで何となく続ける作業と、資源（例: 計算機、時間）が空いているから流す作業は、目的を言えないのでやらない。
- **地図を持つ:** 領域ごとに、段（例: 未踏の開拓、立ち上げ、伸ばす、仕上げ）、今の数字、目標、やめる合図を 1 つの文書にまとめ、周回のたびに書き換える。開拓と深掘りのどちらをしているか、深掘りならどの帯（例: 30% から 60〜70% か、90% 以上か）かを、周回の前にそこで確かめる。配分はオーナーの判断なので、案を示して進め、変えられるようにする。
- **目的に数える数字を決める:** 手段の数字（例: 探索用の経路での成功率）が良くても、目的の数字（再現できる経路での成功率）に数えない。
- **同じものを追い続けていないかを数える:** 周回ごとに、成果物の偏り（最多の型の割合、新しい型の割合）と、入力の使い回しの連続数を数字で出す。偏りが決めたしきい値を超えたら、次の周回の一定の割合を未使用の型から取る。気をつけるのではなく、数える仕組みにする。
- **物差しを先に疑う:** 自分たちの評価に使う物差しは、オーナーの既存の評価で当たるかを確かめてから使う。1 つの標本の系統から出した読みは、別の系統で確かめるまで規則にしない。確かめて外れたら取り下げて記録する。
- **手法そのものも疑う:** 土台は今の手法のまま進める。そのうえで、数字が動かない、同じ失敗が続く、前提が崩れたといった理由があるときに、今の手法（例: 組み立て方、測り方、指示の出し方）を疑い、代わりの手法を考えて、小さな枠で今の手法と並べて試す。全部を新しい手法に入れ替えない。結果は、良くても悪くても今の手法に戻す（採る、直す、捨てた理由を残す）。手法の一覧と試した結果は 1 つの文書に置く。
