# コミットと PR

コミットや PR にする変更は、次の順に進める。

1. **`commit`** スキルに言語のフラグ（`--english` か `--japanese`）を付ける。新しいブランチが要るときは `--branch` も付ける。
   - 整形は、リポジトリのスクリプトやフックが掛ける道具と範囲だけで行い、コミットの前に差分に自分の変えていない塊がないか確かめる。
2. **`create-pr`** スキルに同じ言語のフラグを付け（base が既定でなければ `--base=<base>` も）、draft で作る。
3. **Codex レビュー:** PR の差分（PR が無ければ base との差分）に行う（[codex-review.md](codex-review.md)）。
4. **`simplify`:** コードを変える PR では、最後の Codex ラウンドの後に `origin/<base>...HEAD` に対して毎回行う。省けるのは文書・設定・テストだけか数行の変更で、省いたら理由を報告する。その後、本文を `create-pr --update` で直し `gh pr ready` にする。
5. **CI** が通るまで直す。
   - 緑の印だけでなく CI が出す測定値も読み（読み方は [verification.md](verification.md) の「性能の数字」）、PR 本文に `gh pr edit` で書く（コミットに書くと CI がやり直しになる）。
   - 共有の連番や生成値（例: lockfile、CHANGELOG、migration の番号）を変える PR が並ぶときは、マージの順を先に決め、先頭の PR だけが base を取り込んでマージし、次は新しい base で緑になってから。Why: Git はこれらをテキストとしてマージするので、各 PR が緑でもマージ結果は未検証。
6. **PR のレビューコメント**（AI のレビューを含む）の 1 件ずつに採否を決め、スレッドに返事を書いてからマージする。直したものは commit を、見送るものは理由を書く。resolve はしない（ruleset が要求するリポジトリではオーナーに確かめる）。
   - PR を作る依頼には、その PR の bot のスレッドへの返信も含まれる。triage-review の「明示的に頼まれたときだけ投稿する」は、PR を作る作業の外でレビューだけを頼まれたときの規則として読む。仕事のリポジトリではマージはチームなので、PR を渡す時点で返信を済ませる。
   - bot のスレッドへの返信は、投稿前に triage-review の `references/pr-replies.md` を読み、その書式（常体、挨拶やお礼なし、判定と修正状況と根拠 1 行）に従う。

**言語の決め方:** 既存のコミット履歴の言語に揃える。履歴で決まらない新しいリポジトリでは、公開リポジトリ（OSS）か公開する予定のものは英語、それ以外は日本語。公開リポジトリは `public-text` スキルにも従う。非公開で公開の予定が分からなければ、オーナーに尋ねる。
