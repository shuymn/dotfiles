# 設計判断の基準

## 信頼できる既存の実装と設計を先に調べる

自前で書くのは、信頼できる既存の実装と設計（例: ライブラリ、同じ問題を解く OSS、標準）が扱えない部分だけ。仕組みごとに比べ、採否と理由をリポジトリの一覧（例: `docs/prior-art.md`）に 1 行残す。

- **セキュリティ**（例: JWT/JWKS、HTML サニタイズ、暗号とハッシュ、HTTP 署名、OAuth、URL の解析）は、対象のランタイムで動く確立したライブラリを優先する（例: `jose`）。自前で書くのはプロジェクト固有の規則（例: 認可表、旧形式との互換、リソース上限）だけ。
- 自前で済ませるときは、それらのテストベクタと突き合わせる（例: サニタイザなら DOMPurify・html5lib のテストと OWASP の回避ベクタ、PKCE/JWT なら RFC の付録）。
- 依存を増やすときは、バージョンの固定・`minimumReleaseAge`・catalog で管理する。依存を絞る理由（例: サプライチェーン、バンドルサイズ）と衝突するときは、比べた結果も書く。

- 記録した決定（例: `docs/prior-art.md` の行、設計書）と違う案を出す前に、その行を読み直し、決定を覆す新しい証拠を名指しする。名指しできなければ決定に従う。使う API の範囲が狭いことは、覆す証拠にならない。
- 相手が公開ソースのツール（例: 検証している CLI、依存ライブラリ）なら、観測結果から挙動を推測する前に、検証したバージョンのソースを読んで原因を確かめる。
- 推奨を変えるとき（オーナーの指摘を受けたときを含む）は、変える前に別のモデルを 2 つ以上、結論を伏せた同じ依頼（選択肢を対等に並べ、一次資料を自分で読ませ、確認済みと推測を分けさせる）で独立に検討させ、主張をソースで確かめてから比較・統合する。

## 標準的な手法を先に比べる

回避策を選ぶ前に、その問題で広く使われている標準的な手法（公式のイメージや設定、ドキュメントにある手順）を並べ、それより非標準の手法を選ぶなら理由を書く。動くことと、読み手が「なぜこうしたか」で止まらないことは別の基準として見る。

## リポジトリ全体の一貫性

変更が、既存の同種のコード（例: パターン、ライブラリ、型、エラー、ログ、設定）と同じやり方に揃っているかを確かめる。パターンを変えるなら、残りをどう揃えるかまで決める。新しいライブラリを入れるときは、手書きの同種コードを置き換えるかどうかも決める。型や関数の名前の修飾語（`Parallel`、`Async`、`V2` など）は、対になる実装があるときだけ付ける（対の無い修飾は、存在しない対比を読者に探させる）。

## ミクロの前にマクロ

局所的な対処（例: チューニング、パスごとの特別扱い）を重ねる前に、それが構造の問題の症状でないかを判断する。構造の選択肢と局所的な対処を並べて比べ、推奨を一つ選ぶ。局所的な対処を選ぶなら、それがリポジトリ全体で一貫する規則に収まることを示す。同じ種類の対処が 2 回目に来たら、3 回目を足す前に構造を見直す。

## リポジトリが固定する値を外に写さない

リポジトリが固定している値（例: ツールのバージョン、lockfile が決める依存、設定）は、ビルドのたびにそのコミットから読む。ダッシュボードや CI の変数に写すのは、リポジトリに置けない値（例: デプロイ先の識別子、シークレット）だけにする。写した値は更新の仕組みから外れ、黙ってずれる。

## 未実装は未実装と言う

受け取って黙って捨てる引数や固定値の応答項目は、設計上の選択として説明せず、欠陥として名指しする。

- コードのコメントが「意図的」と書いていても、オーナーの承認が無ければ未承認の過去の判断として扱い、覆してよい。
- 対応状況を数えるときは、引数が保存先まで届き、応答の項目が本物になって初めて「完了」と数える。エンドポイントが 200 を返すだけでは数えない。
