# レビュー

reviewer（Codex・`agy`）はレビュー専用で、実装はさせない。オーナーはこの手順のレビューを経た内容だけを確定版として扱う。

## 実行

- **担当:** コード・資料（骨子を含む）と低区分の完成差分は Codex `gpt-6.2-sol`（high）単体で行う。設計レビュー（設計書・実装計画の審査）だけこれに Antigravity（`agy`）の Gemini 4 Neon（medium。モデルと労力を分けて選ぶ環境では `gemini-4-neon` の medium）を併用し、`agy` 側がエラー（例: クォータ枯渇）で失敗したら無視して `gpt-6.2-sol` の結果だけで進める。
- **依頼と継続:** 編集しないことを依頼文に書く。probe や変異テストを走らせる依頼文には、一時ファイルは `$TMPDIR` に置いてそのまま残すこと（自分で消さない）と、終える前に作業ツリーを元に戻すことを書く。r2 以降の確認ラウンドには修正範囲と前の指摘ごとの対応を渡し、履歴を引き継がない確認には最初の依頼文・指摘・反論も渡す。
- **codex-plugin-cc（`codex-run`）:** 依頼文をファイルに書き、`codex-run --prompt-file <絶対パス> --cwd <worktree> --model gpt-6.2-sol --effort high` を `run_in_background` で走らせ、r2 以降は `--thread <前のラウンドの id>` を足す。結果は `result:` のファイルから読む。probe や変異テストを走らせない資料のレビューは `--read-only` を付ける。
- **agy-plugin-cc（`agy-run`）:** 同じ形で `agy-run --prompt-file <絶対パス> --cwd <worktree> --model gemini-4-neon-medium` を `run_in_background` で走らせ、結果は `result:` から読む。読み取り専用の指定は無く毎回書き込める実行になる。`--thread` は前回の実行が同じディレクトリで返した `thread:` の id があるときだけ足し、別の worktree や id が無いときは新しい会話に前の結果を渡す。同じ作業ツリーで同時に走らせるのは 1 つまで。
- **実行後の確認:** 書き込める実行が起動した後は、失敗時も含めて `changes:` を読み、`none` 以外（`unknown` や欠落を含む）ならプロセス終了と作業ツリーを確かめてから次へ進む。`scratch left:` はプロセス終了と対象を確かめてから `trash` で片付ける。

## いつ

区分は行数や revert のしやすさではなく、変更後に何に作用するかで決め、迷ったら上の区分にする。simplify は回数に数えない。

- **低**（文書・設定・テストだけを変える修正、短い資料）: 計画と主張の一覧は作らず、完成した差分に 1 回、計画と資料の観点で。修正の確認は、修正が意味を変えたときだけ。
- **標準**（普通のコード、長い資料）: 計画（資料は骨子）と完成物に各 1 回。直す指摘が出たら確認のラウンドを足す。
- **高**（認可、課金、データの移行、公開の API とデータ形式、CI・リリース・インストーラ、セキュリティの境界、戻せない操作）: 標準に加え、確認のラウンドを省かず、マージの前に目的の層を実物で確かめる（本番でしか確かめられないものは隔離した環境で本番と同等のパスを通す）。できなければ未検証と報告し、扱いをオーナーと決めるまでマージしない。

## 依頼の書式

範囲を限り、変更の目的、設計書・指示書・ブランチが足したもの、確かめたい問いを名指しし、範囲外にしたものは理由付きで渡す。HIGH/MEDIUM は file:line・シナリオ・修正案を付けて重要度順に、LOW は 1 行ずつ返させる。検査や監査（例: テストの仕組み、lint、計画の監査）のレビューでは、それが何から守るか（書き手のうっかりか、検査を通すよう意図された入力か）を依頼に書く。reviewer の常時の項目（[attention.md](attention.md)）は依頼文に貼る。

依頼文は、確かめたい失敗を中立の言葉で書く（「フィクスチャの外に書けるか」「所有を確かめずに消すか」）。攻撃・被害者・すり抜けといった語を並べない。Why: 並べた依頼は、提供元の判定で止まることがある。

**計画と資料**は次を同じ重みで見させる。

1. **設計:** 外部仕様との契約、データモデルと層、単純さとコスト、リポジトリ全体との一貫性。
2. **バグの芽:** エッジケース、全方向のページング、競合、再開、エラー処理。
3. **セキュリティ:** 脅威モデルがあればその不変条件。
4. **テスト:** 主張ごとのテストが、修正を戻して落ちる形か、検証が素通りするフィクスチャが無いか。
5. **主張の一覧**（[orchestration.md](orchestration.md) の「目的の層と計画の層」）: 出どころが無い、目的や範囲を超える、破れたことを示しようがない、既存の要件が漏れている、受け入れ済みの制限を守ろうとしている主張。
6. **決定の洗い出し:** 設計書の決定・補足・「受け入れる」と書かれた結果を列挙させ、利用者に見える変化があるものごとに、目的を損なわない根拠があるかを判定させ、根拠の無いものを入力と変更前後の結果付きで返させる（[SKILL.md](../SKILL.md) の手順 5）。

**コード**は「レビューして」と頼まず、主張の一覧を渡して反証させる。主張ごとに、反証の証拠（下）、守るテストの名前、守るテストが無いこと（テストの欠落）のどれかを返させる。守るテストが主張を壊したコードでも落ちないなら、それも反証とする。あわせて 3 つを問う。

- 主張が「成功する」「拒否しない」の形のとき、その結果が使える成果物か（機能や表示を失っていないか）。具体的な入力と、変更前と変更後の結果を返させる。
- 計画に従うと目的が悪くなる所、主張そのものの誤り。証拠は目的の層の条件が実物で落ちる例か外部仕様との矛盾で、計画の層がすべて通っていても採る。
- 一覧に無い既存の要件を破る所。要件は正本（設計書の契約、脅威モデルの守るもの）と、計画が変えるとしていない今の振る舞い（base で通り変更後に落ちる反例で示す。偶然の振る舞いは除く）。正本にも今の振る舞いにも無い防御や汎用化は足させない。

## 反証の証拠

コードの指摘で採るのは次のどれかを持つものだけで、無ければ LOW までとする。計画と資料の指摘は、引用した本文・出どころ・シナリオ・設計の論拠で判断する。

- そのまま走らせられるテストか再現のコマンド（入力、期待、今のコードで起きること。規模やアロケーションのテストを含む）。
- 競合なら、ソースの位置を挙げた割り込みの順序と、入れるべき待ち点（[verification.md](verification.md) の決定的な並行性のテスト）。
- 引用した要件や外部仕様（`file:line`）と実装との矛盾。
- コードと想定する利用規模から導いたリソース消費の計算。

## 取捨選択

1. **反例は自分で走らせる:** テストが走ったことと、期待が主張に根拠を持つことを確かめ（[verification.md](verification.md) の「証拠の強さ」）、主張どおりの理由で落ちたものだけを再現とする。走らなかったか効いていないものは結論なし、正しく作って通ったものは退ける。変異テストがあれば、守るテストが本当に落ちるかも確かめる。走らせられない証拠は、ソースと定数を辿り直してから採る。重要度は示された影響で決める。
2. **脅威モデル:** 脅威の前提が採否を決める指摘だけに使い、普通の正しさは設計の契約で決める。守るもの（回帰防止の上限を含む）を破るなら採る。受け入れ済みの制限は、条件がすべて当てはまり守るものを破らないときだけ見送る。どちらでもない新しい守りや方針の食い違いは、直さずにオーナーへ相談し、方針が変わるなら先に脅威モデルを直す。
3. **目的に照らす:** ラウンドの回数に上限は無く、指摘を 0 件にすることは目的でもない。「この変更の目的に必要か」「実際に起こるか」で採否を決め、理由を添えて報告する。起こり得ない入力への防御や要件外の汎用化は見送る。最後のラウンドで MED 以上を見送るときは、理由が指摘のシナリオ全体に当てはまるかを確認のラウンドで確かめる。意味や予算の配分を変える修正は、上限と外部仕様に照らしてから送る。仕組みを足す修正は、部品を外すか狭めて問題が消えないかを先に問う。使い手がエージェントのツールでは、まれな失敗は扱い切らず、呼ぶ側が気づける報告（「不明」とその理由を含む）で足りるかを先に問う。
4. **計画への指摘は計画を直す:** 退けず、計画を直してから要ればコードを直す。
5. **同じ種類の指摘が 3 ラウンド（設計の範囲を広げる指摘は 2 ラウンド）続いたら:** 修正を重ねる前に作り直す（[orchestration.md](orchestration.md) の「作り直しの向き」）か、制約として文書化して見送る。
