# 検証

## 繰り返す欠陥を機械に見つけさせる

繰り返す欠陥には、指示書に規則を足す前に、誤った形を機械が見つけられるようにする。効く順に、構造（誤った形を書けない型や API、規則を 1 か所に集める）、下の表のテスト、静的検査（ソースや migration を読むテスト、lint の規則）、指示書の共通規則。どれも普通のテストのコードとして書く。

実物から証拠を集めて判定するハーネス（例: spike、実機の検査）は、最初のバージョンから判定を 1 つの関数に集め、結果を型で分ける。不合格が確定した失敗は `fail`、正の証拠が揃ったときだけ `pass` とし、判定の確定に必要な証拠の欠落・観測の失敗・未実行は `inconclusive` にする。計画のレビューでは、受け入れ条件ごとに、証拠が欠けたまま `pass`（`go`）になる道を挙げさせる。

別の言語や形式（例: SQL のスキーマ、HTML、画像のバイト列）を判定する静的検査は、最初からその処理系自身が返すもの（例: 適用後のスキーマの一覧、パーサーの構文木や DOM ツリー、デコード結果）を比べて作る。テキストを自前で解析するのは、処理系が報告しないことだけにする。

| 手法 | 捕まえる失敗 | 使いどき |
|---|---|---|
| 参照モデルとの照合（テスト内の小さなモデルと対象実装の実行結果を突き合わせる） | パスごとに規則がずれる（例: 公開範囲、認可、配送先） | 同じ規則が多くのパスにまたがるとき |
| プロパティベーステスト | エッジケース、組み合わせ | 入力の空間が広いとき。反例が出たら生成器を狭めず、反例を報告する |
| 定数から導く上限 | 実測値に頼った予算の破綻 | 上限やバイト数が仕様に含まれるとき。上限はテストが定数から計算し、実測値は上限以下であることの確認に使う |
| 実行計画の確認（本番の SQL の `EXPLAIN` を上限いっぱいのデータで） | 規模が大きくなったときの全件走査 | 大きなテーブルを問い合わせるとき |
| 決定的な並行性のテスト（一方を明示的な待ち点で止め、他方をコミットさせる） | 競合、二重実行 | 状態を共有するパス。並べて走らせるだけでは待ち点にならない |
| モデル検査・形式証明 | 喪失・重複・順序・再試行が重なると破れる不変条件 | レビューやランダム順のテストが毎回新しいパスを出すとき。設計フェーズで検査し反例を回帰テストに |

モデルには写したファイルのハッシュを記録し、変わると落ちるテストを置く。落ちたらモデルを照らし直してからハッシュを進める。反例は回帰テストにし、コードか設計で辿れない遷移を名指せたときだけモデルの誤りとする。

## 証拠の強さ

主張（例: この変更は安全、このテストは回帰を捕まえる）は、安く届く範囲で次のレベルを上がり、どのレベルで止まったかを報告する: 言っただけ → `file:line` かライブラリのソースを指した → 本物のコードを呼び、間違っていれば大きく落ちるスクリプトかテストを走らせた → 動いているアプリで再現した。

- 変更の安全は、たいてい 1 つの事実に支えられている。それを名指しし、実行検証レベルまで上げる。
- 回帰テストは、修正を外して落ち、戻して通るのを見て初めてそう呼ぶ。
- 測定や検査は、主張しているパスを本当に通ったことも確かめる（例: ログの項目、結果の形）。CI のジョブやキャッシュを足した PR では CI 成功の印で済ませず、最初の実行のログでキーや入力が意図どおりに展開されたかを読む。
- 記録から数えた数値をオーナーの判断材料にする前に、数えた元の行を数件出し、条件が意図した項目を見ているかを確かめる。数えた項目が、指示書や作成時の条件（例: 書かせたタグ）で生じたものでないかも確かめる。
- 検証（テスト一式、pre-push 付きの push）は、フォアグラウンド・バックグラウンドを問わず出力の全体をファイルに残してから要約を読む。

## 実アプリで確かめる

実際に動かして確かめる場面が繰り返すのに、リポジトリに `.claude/skills/verify-<app>/` が無ければ作る。中身（空のデータから使える状態までの起動と、応答するだけでなく使えることでの準備完了の見分け方、操作してよい実体かの読み取り専用の確認、本物のセレクタやコマンド、証拠の残し場所、自分が起動したものだけの片付け）はリポジトリから調べて書き、一度通しで走らせてから使う。

外部ソフトウェア（例: フェデレーション相手、クライアント、外部サービス）を使う実物での確認を指示書にする前に、シナリオの各ステップの前提をコードで確かめる。相手が実際に送る形（そのバージョンのソースにその属性や署名があるか）と、こちらが受け付ける条件の両方を見る。成り立たないステップがあれば、その役を務められる別のソフトウェアを最初から選ぶ。

## 性能の数値

数値を報告する前、または数値で選ぶ前に確かめる。

- **条件:** 両側を本番と同じ設定・バージョン・データ（例: リリースビルド、本番のフラグ、揃えたデータ）で走らせる。片側がデフォルト値や欠けたデータなら、実装ではなく条件を比べている。
- **実行と上限:** 失敗の件数、出力の正しさ、作業が計測区間で本当に行われたかを確かめる。変えた部分が占めていた時間や帯域から出る上限を超える数値は、説明がつくまで不具合として扱う。
- **ばらつき:** 手元の数値は負荷でばらつくので目安とし、細かい差を追わない。比べるときは両側を交互に数回走らせて中央値と幅を出し、幅より小さい差は差なしとする。判断を左右する数値は、決定的な作業量（例: 読んだ行数）か、同じ CPU の型と負荷での比較で決め、型を記録する。

条件が揃っていない、実行を確かめていない、のどちらかなら「結論なし」とし、欠けを名指す。
