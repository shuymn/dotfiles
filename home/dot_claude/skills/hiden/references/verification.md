# 検証

## 繰り返す欠陥を機械に見つけさせる

繰り返す欠陥には、指示書に規則を足す前に、誤った形を機械が見つけられるようにする。効く順に、構造（誤った形を書けない型や API、規則を 1 か所に集める）、下の表のテスト、静的検査（ソースや migration を読むテスト、lint の規則）、指示書の共通規則。どれも普通のテストのコードとして書く。

| 手法 | 捕まえる失敗 | 使いどき |
|---|---|---|
| 参照モデルとの照合（テストの中に小さな参照モデルを書き、本物の経路の結果と突き合わせる） | 経路ごとに規則がずれる（公開範囲、認可、配送先） | 同じ規則が多くの経路にまたがるとき。規則を変える PR では、モデルも同じ PR で変える |
| 性質ベースのテスト | 端の入力、組み合わせ | 入力の空間が広いとき。反例が出たら生成器を狭めず、反例を報告する |
| 定数から導く上限 | 実測値に頼った予算の破綻 | 上限やバイト数が仕様に含まれるとき。上限はテストが定数から計算し、実測値はそれ以下であることの証人にする |
| 実行計画の証明（`EXPLAIN` などを本番の SQL で、上限いっぱいのデータに対して） | 規模が大きくなったときの全件走査 | 大きな表を問い合わせるとき |
| 決定的な並行性のテスト（一方を明示的な待ち点で止め、他方をコミットさせる） | 競合、二重実行 | 状態を共有する経路。同時に走らせるだけ（`Promise.all` やゴルーチンを並べるだけ）では待ち点にならない |

## 証拠の強さ

主張（この変更は安全、このテストは回帰を捕まえる、この数字は正しい）は、安く届く範囲で次の段を上がり、どの段で止まったかを報告する: 言っただけ → `file:line` かライブラリのソースを指した → 本物のコードを呼び、間違っていれば大きく落ちるスクリプトかテストを走らせた → 動いているアプリで再現した。

- 変更の安全は、たいてい 1 つの事実に支えられている。それを名指しし、走らせる段まで上げる。
- 回帰テストは、修正を戻して落ち、戻して通るのを見て初めて回帰テストと呼ぶ。
- 測定や検査は、主張している経路を本当に通ったことも確かめる（ログの項目、結果の形）。
- 検証（テスト一式、pre-push 付きの push）は、前面・背景を問わず出力の全体をファイルに残してから要約を読む。末尾だけを残すと、落ちた検査が再現しなかったときに何が落ちたか分からず、間欠的な失敗を CI まで持ち越す。

Why: 筋の通った説明は、正しくても誤っていても同じように読める。走らせた証拠なら、確かめ直さずに次の判断を載せられる。

## 実アプリで確かめる

実際に動かして確かめる場面が繰り返すのに、リポジトリに `.claude/skills/verify-<app>/` が無ければ作る（組み込みの `run` もこれを先に探す）。中身（空のデータから使える状態までの起動と、応答するだけでなく使えることでの準備完了の見分け方、操作してよい実体かの読み取り専用の確認、本物のセレクタやコマンド、証拠の残し場所、自分が起動したものだけの片付け）はリポジトリから調べて書き、一度通しで走らせてから使う。

## 性能の数字

数字を報告する前、または数字で選ぶ前に確かめる。

- **条件:** 両側を本番と同じ設定・版・データ（リリースビルド、本番のフラグ、本番が読む表を揃えた計測用データ）で走らせる。片側が既定値や欠けたデータなら、実装ではなく条件を比べている。
- **実行と上限:** 失敗の件数、出力の正しさ、作業が計測区間で本当に行われたかを確かめる。変えた部分が占めていた時間や帯域から出る上限を超える数字は、説明がつくまで不具合として扱う。
- **揺れ:** 手元の PC は並行する開発や私用で負荷が変わるので、手元の数字は目安として扱い、細かい差を追わない。比べるときは両側を交互に数回走らせて中央値と幅を出し、幅より小さい差は差なしとする。判断を左右する数字は CI など負荷の安定した環境で取る。

条件が揃っていない、実行を確かめていない、のどちらかなら「結論なし」とし、欠けを名指す。
