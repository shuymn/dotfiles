# 検証手法の選択

繰り返す欠陥には、指示書に規則を足す前に、誤った形を機械が見つけられるようにする。効く順に:

1. **構造:** 誤った形を書けない型や API にし、規則を 1 か所に集める。
2. **実際に動かすテスト:** 下の表の手法。
3. **静的検査:** テストとして書いた検査や lint の規則。
4. **指示書の共通規則。**

| 手法 | 捕まえる失敗 | 使いどき |
|---|---|---|
| 参照モデルとの照合（テストの中に小さな参照モデルを書き、本物の経路の結果と突き合わせる） | 経路ごとに規則がずれる（公開範囲、認可、配送先） | 同じ規則が多くの経路にまたがるとき。規則を変える PR では、モデルも同じ PR で変える |
| 性質ベースのテスト | 端の入力、組み合わせ | 入力の空間が広いとき。反例が出たら生成器を狭めず、反例を報告する |
| 定数から導く上限 | 実測値に頼った予算の破綻 | 上限やバイト数が仕様に含まれるとき。上限はテストが定数から計算し、実測値はそれ以下であることの証人にする |
| 実行計画の証明（`EXPLAIN` などを本番の SQL で、上限いっぱいのデータに対して） | 規模が大きくなったときの全件走査 | 大きな表を問い合わせるとき |
| 検査として書く静的解析（ソースや migration を読むテスト、lint の規則） | 書いてはいけない形 | 同じ指摘がレビューで繰り返すとき |
| 決定的な並行性のテスト（一方を明示的な待ち点で止め、他方をコミットさせる） | 競合、二重実行 | 状態を共有する経路。同時に走らせるだけ（`Promise.all` やゴルーチンを並べるだけ）では待ち点にならない |

- どれも普通のテストのコードとして書く。
- 測定や検査は、主張している経路を本当に通ったことも確かめる（ログの項目、結果の形）。良すぎる数字は、説明がつくまで不具合として扱う。
