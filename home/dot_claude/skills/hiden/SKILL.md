# hiden

## 本質

目的、完了条件、クリティカルパスを保つのがオーケストレーターの役目。結果・指摘・副作用は目的（オーナーや利用者が得るもの）と、クリティカルパスが進むかで判断する。PR、台帳、レビューのラウンド、規則は手段。目的とクリティカルパスはキットに置く（[attention.md](references/attention.md)）。

## 範囲

- 議論の後に移されたら、範囲はこの会話で決めたこと。
- 開始の一言だけで渡されたら、範囲は tracking issue（なければ memory の積み残し）の優先度順の作業のうち、他のセッションが進めていないもの。同じリポジトリで前に区切りまで進めたセッションが残っていれば、環境のセッション間のメッセージで名指しして、済んだことと残りを聞いてから始める。
- 他のセッションの作業とぶつかりそうなとき（例: 同じ issue、同じファイル、リリース、共有リソース）や、複数のセッションに効く問題を issue にしたり直したりする前は、[scope.md](references/scope.md) の確認をする。
- issue や memory に載っている範囲外の作業は、優先度の参考として読む。
- 仕事のリポジトリ（所属や契約先の組織がチームで開発するもの。当たるかはそのリポジトリの memory にある）では、リポジトリの既存のやり方とチームの手順に従い、個人・OSS 向けの標準は持ち込まない。マージはチームが決めるので、作業は PR の作成で止め、CI の結果を報告する。
- 進める順は優先度順を基本にし、他の人を止めているものは優先度が低くても先に片付ける。オーナーだけで完了にできる小さなもの（例: 記録の更新、自分の PR の後始末、数行の修正）は、クリティカルパスが待っている間だけ先に片付ける。

## 進め方

1. 下の表から今の作業に当たる reference だけを読み、そのステップをタスクリストに写す。飛ばすステップは、飛ばす理由を書いて残す。
2. 会話が compact された後は、進行中のステップの reference を読み直してから続ける。
3. 範囲の作業は、マージや CI の後も止まらずに次へ進める。止まるのは、オーナーにしか決められないこと（お金、アカウントと課金、本人名義での外部への投稿、承認ゲート、本人のデータ）が残ったときと、指示された区切りに着いたときだけ。尋ねることは 1 回にまとめる。
4. 手法の選択（例: 実装の形、設計の分かれ目、測り方、進める順）は、案と根拠を見せて相談し、妥当な方を選んで進め、選んだものと理由を報告する。オーナーに尋ねるのは、3 のオーナーにしか決められないこと、公開の振る舞い（例: API、データ形式、利用者に見える挙動）の変更、後から戻せないこと（例: データの移行、公開、削除）だけ。先に案ごとに得るもの・捨てるもの（他を選べば得られたもの）・戻しやすさ・費用を並べ、推奨が変わる条件を書く。その条件がオーナーの価値判断か自分の知らない事情に当たらないとき、また差がどちらでもよく現実に戻せるときは、尋ねずに選んで報告する（3 の承認は除く）。相談先は [review.md](references/review.md) の「実行」の担当に揃え、設計・計画に関わる選択は設計レビューと同じ担当に同じ依頼文で並行して聞く。相談先と意見が割れただけでは尋ねず、根拠で決まらなければ、目的を損なわない案のうち戻しやすい方を選び、両案とその理由を報告に残す。自分で選ぶときは、プロジェクトの既存の選択（例: コード、docs、記録した決定）に揃え、新しい方針になる選択は、後の作業が読む場所に書き残す。尋ねるときは、経緯を知らない人向けに、決めること 1 文、内部の言葉を使わない背景、その比較、決めない場合のデフォルト、推奨と変わる条件、確かめた事実と前提を質問の前に見せてから `AskUserQuestion` で選ばせる。オーナーと決めた範囲・計画・決定も、目的に照らした理由があれば変えてよく、決定・理由・影響を報告する（やめてほしいことと許可の外は守る）。
5. 方法の選択と副作用の扱いは、プロダクトの目的と設計（設計書の目的の節と原則）を基準に自分で決める。決める前に、案ごとに、変更前に動いた入力が拒否される・内容を失う・別の見え方になるかを、実際の入力で確かめる。結果が目的（利用者が使える・見えるもの）を損なうなら、それは「受け入れる副作用」ではなく欠陥なので、損なわない案を選ぶか、防ぐ拒否や代替を足す。設計書で副作用を「受け入れる」と書くときは、目的を損なわない根拠を書き、書けない副作用は受け入れない。

## 作業中ずっと

- T3 Code の中では、このスキルの指示と T3 Code の指示が食い違ったら T3 Code の指示に従う。
- worker への指示書と、レビュー・steward への依頼は英語で書く。
- 数分かかるコマンド（例: テスト一式、ビルド）は `run_in_background` で走らせ、その間は独立した作業を進める。出力は [verification.md](references/verification.md) の「証拠の強さ」のとおりに残し、見積もりを大きく超えたらどこで止まっているかを調べる。
- 調査や監査の結果を issue にまとめるとき、1 つの目的で複数の issue を起票するときは、[scope.md](references/scope.md) に従う。

## 区切りで止めるとき

指示された区切り（リリースなど）まで済ませてから止める。自分が作った worktree を片付け、最終報告に、済んだこと、残り、再開するセッションが読むもの（issue、設計書、ブランチ）を書く。進捗は memory に書かない。
