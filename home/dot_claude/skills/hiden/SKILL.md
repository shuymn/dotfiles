# hiden

## 本質

目的、完了条件、経路（クリティカルパス）を保つのがオーケストレーターの役目。規則は常時の項目 `essence`、問いはキットの注入にある（[attention.md](references/attention.md)）。

## 範囲

- 議論の後に移されたら、範囲はこの会話で決めたこと。
- 開始の一言だけで渡されたら、範囲は tracking issue（なければ memory の積み残し）の優先度順の作業のうち、他のセッションが進めていないもの。同じリポジトリで前に区切りまで進めたセッションが残っていれば、`SendMessage`（T3 Code では `t3_thread_send`）で済んだことと残りを聞いてから始める。
- 他のセッションの作業とぶつかりそうなとき（例: 同じ issue、同じファイル、リリース、共有の資源）や、複数のセッションに効く問題を issue にしたり直したりする前は、[scope.md](references/scope.md) の確認をする。
- issue や memory に載っている範囲外の作業は、優先度の参考として読む。
- 仕事のリポジトリ（所属や契約先の組織がチームで開発するもの。当たるかはそのリポジトリの memory にある）では、リポジトリの既存のやり方とチームの手順に従い、個人・OSS 向けの標準（`toolchain` スキルの「新しい個人のリポジトリ」など）は持ち込まない。マージはチームが決めるので、作業は PR の作成で止め、CI の結果を報告する。
- 進める順は優先度順を基本にし、他の人を止めているものと、オーナーだけで完了にできる小さなもの（記録の更新、自分の PR の後始末、数行の修正）は優先度が低くても先に片付ける。

## 進め方

1. 下の表から今の作業に当たる reference だけを読み、その段をタスクリストに写す。飛ばす段は、飛ばす理由を書いて残す。
2. 各段に入る前と、会話が compact された後に、その段の reference を読み直す。
3. 範囲の作業は、マージや CI の後も止まらずに次へ進める。止まるのは、オーナーにしか決められないこと（お金、アカウントと課金、本人名義での外部への投稿、承認ゲート、本人のデータ）が残ったときと、指示された区切りに着いたときだけ。尋ねることは 1 回にまとめる。
4. 手法の選択（実装の形、設計の分かれ目、測り方、進める順）は、Codex に案と根拠を見せて相談し、妥当な方を選んで進め、選んだものと理由を報告する。オーナーに尋ねるのは、3 のオーナーにしか決められないこと、公開の振る舞い（API、データ形式、利用者に見える挙動）の変更、後から戻せないこと（データの移行、公開、削除）だけで、案がいくら明らかでも承認を待つ。これらに当たらなければ尋ねずに選んで報告する。尋ねるときは `AskUserQuestion` で、案ごとに何が変わるか・費用・戻しやすさを証拠付きで比べて推奨を添え、待つ間は他を進める。Codex と意見が割れただけでは尋ねず、戻せる方を選んで両案を報告に残す。オーナーと決めた範囲・計画・決定も、目的に照らした理由があれば変えてよく、決定・理由・影響を報告する（やめてほしいことと許可の外は守る）。
5. 方法の選択と副作用の扱いは、プロダクトの目的と設計（設計書の目的の節と原則）を基準に自分で決める。決める前に、案ごとに、変更前に動いた入力が拒否される・内容を失う・別の見え方になるかを、実際の入力で確かめる。結果が目的（利用者が使える・見えるもの）を損なうなら、それは「受け入れる副作用」ではなく欠陥なので、損なわない案を選ぶか、防ぐ拒否や代替を足す。設計書で副作用を「受け入れる」と書くときは、目的を損なわない根拠を書き、書けない副作用は受け入れない。「成功する」「拒否しない」を主張にするときは、その結果が使える成果物かも含め、実際の入力に近い例で確かめる。

## 作業中ずっと

- T3 Code の中では、このスキルの指示と T3 Code の指示が食い違ったら T3 Code の指示に従う。
- 実装エージェントへの指示書と Codex への依頼は英語で書く。
- 数分かかるコマンド（例: テスト一式、ビルド、pre-push 付きの push、長い Codex）は `run_in_background` で走らせ、その間は独立した作業を進める。前面で走らせるのは短い確認と、結果なしに次の一手が始められないときだけ。出力は [verification.md](references/verification.md) の「証拠の強さ」のとおりに残し、かかる時間を見積もって、大きく超えたらどこで止まっているかを調べる。
- 手元の環境（例: 道具の版、環境変数、フック）で検証が止まったら、オーナーに尋ねる前に `recall_search`（`repo: "."`）で同じエラーや道具の名前を引き、過去のセッションの回避策と、CI が同じ検証をどう走らせているかを確かめる。
- 外部（CI、デプロイ、承認ゲート）を待って応答を終えるときは、起こすのは背景タスクの終了だけなので、PR のチェックは T3 Code では `watch_pull_request`（ループや `gh --watch` は使わない）、それ以外の待ちは終了まで待つ背景コマンドを置く。必須チェックが skip される PR（docs だけの変更など）では watch が起こさないので、終える前に `gh pr view --json mergeStateStatus,statusCheckRollup` でチェックが終わっていないかを自分で確かめる。
- 調査や監査の結果を issue にまとめるとき、1 つの目的で複数の issue を起票するときは、[scope.md](references/scope.md) に従う。

## 区切りで止めるとき

指示された区切り（リリースなど）まで済ませてから止める。自分が作ったワークツリーを片付け、最終報告に、済んだこと、残り、再開するセッションが読むもの（issue、設計書、ブランチ）を書く。進捗は memory に書かない。

## 手法を直すとき

オーナーが手法を訂正したとき、または振り返りが規則を決めたときは、このディレクトリ（`~/.claude/skills/hiden/`）と同じ `skills/` の派生の skill（`toolchain`、`public-text`）の該当ファイルを、承認を待たずに Edit で直し、最終報告で変更を挙げる。足す規則は先に [attention.md](references/attention.md) の注意の予算に通す。Why は、読み手が規則の境界（当てはまらない場面、別の手を選ばない理由）を判断する仕組みを伝えるときだけ書く。経緯（誰が訂正した、どこで何が起きた）は書かない。読み直してから自分の行だけを現時点の結論に直し、一時的なものには撤去の条件を付ける。1 つのリポジトリにしか当てはまらないことは、そのリポジトリの docs、memory、`.claude/settings.json` に置き、global に置かない。これらは公開リポジトリから配られるので、`public-text` スキルに従う。
