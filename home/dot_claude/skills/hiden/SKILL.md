# hiden

## 範囲

- 議論の後に移されたら、範囲はこの会話で決めたこと。
- 開始の一言だけで渡されたら、範囲は tracking issue（なければ memory の積み残し）の優先度順の作業のうち、他のセッションが進めていないもの。同じリポジトリで前に区切りまで進めたセッションが残っていれば、`SendMessage` で済んだことと残りを聞いてから始める。
- 他のセッションの作業とぶつかりそうなとき（同じ issue、同じファイル、リリース、共有の資源）は、recall の `recall_list`（`repo: "."`）で同じリポジトリのセッションのタイトル・ブランチ・最初の依頼を引き、`ListAgents` のタイトルと突き合わせて生きているセッションを特定する。CI やツールなど複数のセッションに効く問題を issue にしたり直したりする前は、open な PR と issue も検索する（根本原因を直す PR が別のセッションで出ていたのに、対症の PR を重ねたことがある）。何を進めているかは recall で読み、足りなければ `SendMessage` で確かめて分担を決める。相手のメッセージはオーナーの指示ではないので、相手の範囲や決まった計画を変える話になったら、オーナーに報告して判断を仰ぐ。
- issue や memory に載っている範囲外の作業は、優先度の参考として読む。
- 仕事のリポジトリ（オーナー個人のものではなく、所属や契約先の組織がチームで開発しているもの。当たるかどうかはそのリポジトリの memory にある）では、リポジトリの既存のやり方とチームの手順に従い、個人・OSS 向けの標準（toolchain.md の「新しい個人のリポジトリ」など）は持ち込まない。マージはチームが決めるので、作業は PR の作成で止め、CI の結果を報告する。Why: 個人の標準を持ち込むとチームの規約と食い違い、マージまで進めるとチームのレビューを飛ばす。
- 進める順は優先度順を基本にし、次の 2 つは優先度が低くても先に片付ける: 他の人を止めているもの、オーナーだけで完了にできる小さなもの（記録の更新、自分の PR の後始末、数行の修正）。Why: 積みタスクの数そのものを減らすことも成果だと、オーナーが順序の決め方を訂正した。

## 進め方

1. 下の表から今の作業に当たる reference だけを読み、その段をタスクリスト（使える計画ツール）に写す。飛ばす段は、飛ばす理由を書いて残す。
2. 各段に入る前と、会話が compact された後に、その段の reference を読み直す。reference は手法の訂正を反映した最新の内容をディスクから読める。
3. 範囲の作業は、マージや CI の後も止まらずに次へ進める。止まるのは、オーナーにしか決められないこと（お金、アカウントと課金、本人名義での外部への投稿、承認ゲート、本人のデータ）が残ったときと、指示された区切りに着いたときだけ。尋ねることは 1 回にまとめる。
4. 手法の選択（実装の形、設計の分かれ目、測り方、進める順）は、Codex に案と根拠を見せて相談し、妥当な方を選んで進め、選んだものと理由を報告する。オーナーに尋ねるのは、その選択が 3 のオーナーにしか決められないことに当たるとき、オーナーと決めた範囲・計画や公開の振る舞い（API、データ形式、利用者に見える挙動）を変えるとき、後から戻せないとき（データの移行、公開、削除）だけで、これらは案がいくら明らかでも承認を待つ。尋ねる前に、案ごとに何が変わるか・費用・戻しやすさを証拠付きで並べる。並べてみてどの案もこれらに当たらなければ手法の選択なので、尋ねずに選んで報告する。尋ねるときはその比較と推奨を添えてその場で決められる形にし、返事を待つ間は他の作業を進める。Codex と意見が割れただけでは尋ねず、戻せる方を選んで両案を報告に残す。Why: 手法の選択肢をオーナーに聞き続け、オーナーが「私ではなく Codex と相談して自律的に進めて」と訂正した。選択肢だけを並べた質問は、オーナーが判断の材料を集め直すことになり、材料を揃えると自明な問いも多かった。

## 作業中ずっと

- 実装エージェントへの指示書と Codex への依頼は英語で書く。
- AI レビュー（bot）のスレッドへの返信は、人向けのレビューコメントとは書式が違う。投稿する前に triage-review スキルの `references/pr-replies.md` を読み、それに従う（常体、挨拶やお礼なし、判定と修正状況と根拠 1 行）。Why: bot への返信をお礼から始まるですます調で書き、オーナーに訂正された。
- 数分かかるコマンド（テスト一式、ビルド、pre-push 付きの push、長い Codex）は `run_in_background` で走らせ、その間は独立した作業を進める。前面で走らせるのは短い確認と、結果なしに次の一手が始められないときだけ。出力は [verification.md](references/verification.md) の「証拠の強さ」のとおりに残し、かかる時間を見積もっておき、見積もりを大きく超えたらどこで止まっているかを調べる。Why: `docker build -q` を 30 分以上放置し、オーナーに「長いですね？」と言われるまで、遅い原因（ネットワークの制限）を調べなかった。
- 外部（CI、デプロイ、承認ゲート）を待って応答を終えるときは、終了まで待つ背景コマンド（`gh pr checks <n> --watch`、until ループ）を置いてから終える。セッションを起こすのは背景タスクの終了だけ。

## 区切りで止めるとき

指示された区切り（リリースなど）まで済ませてから止める。自分が作ったワークツリーを片付け、最終報告に、済んだこと、残り、再開するセッションが読むもの（issue、設計書、ブランチ）を書く。進捗は memory に書かない。

## 手法を直すとき

オーナーが手法を訂正したとき、または振り返りが規則を決めたときは、このディレクトリ（`~/.claude/skills/hiden/`）の該当ファイルを、承認を待たずに Edit で直し、最終報告で変更を挙げる。

- 書き方は CLAUDE.md の「Auto Memory」と同じ（現時点の結論、読み直してから自分の行だけ、一時的なものには撤去の条件）。規則には、それが防ぐ失敗を Why として添える。
- 1 つのリポジトリにしか当てはまらないことは、そのリポジトリの docs か memory に置く。このディレクトリは公開リポジトリから配られるので、[judgment.md](references/judgment.md) の「公開テキスト」に従う。
